# I-059 派发脚手架设计与交付（2026-10-03）

> 事项 I-059：HQ 派发脚手架，自动生成临时员工会话简报，机主一键发队。
> 本文件为设计与交付记录。生成器为 items_registry/brief.py，随本次
> 提交交付。

## 一、问题与方案

派一个新会话当施工队，过去由机主人肉完成：记住贴什么开工卡、判断贴
的版本是否现行、手动写明路线身份。人肉环节有三个缺陷：版本可能陈旧、
内容靠记忆不全、过程不留档。本交付把这套仪式压缩为一条命令：

    python items_registry/brief.py L3

命令输出一段自足简报，整段复制进新会话，该会话即具备开工所需的全部
上下文。

## 二、简报内容与可追溯来源

判据要求简报内容全部可追溯账本。实现口径为只做现算：生成时刻从账本
文件与规则文件读出，生成器不写死任何会过期的数据。六个板块与来源
对应如下。

一为路线身份：路线名、使命、独占领地、参数改值权限、重构权限，来源
items_registry/lanes.json。二为本路现状：总账计数与第一条可领事项，
来源 items_registry/items.json 加 items_registry/schedule.py 的拓扑
分层。可领口径与开工卡一致，按层与编号排序取第一条未认领、未阻塞、
依赖已清的事项，输出该事项的销项判据、备注、依赖、在档证据数与一条
可直接粘贴的认领命令。三为开工卡现行全文：生成时刻从
协作架构_20260930.md 第三节现读，不内嵌副本。四为禁区清单：他路
独占路径逐条列出并标注归属。五为红线速查：领地、在制限制、租约、
语言三类违规（词表以 items_registry/banned_words.json 为准）、汇报
七段格式、完成判定的唯一口径、新问题走待审队列。六为命令速查：看板、
自查、总账、语言自查四条。

开工卡正文随规则演进会变化（本事项施工时已为九条版本，与机主此前
手贴的七条版本不同），现读机制保证简报永远携带现行版。

## 三、验证记录

三路生成与一处边界全部通过。L3 简报正确选中最顶卡事项并给出判据与
认领命令。L1 简报正确选中其看板首条。L2 在其事项全部为已认领或阻塞
状态时，简报如实报告无可领并指示待命，不虚构任务。不存在的路线以
非零退出码报错并列出可选路线。生成器仅用标准库 json、os、re、sys、
datetime，零第三方依赖。lanes.json 共享区键缺失时，生成器与
check_commit.py 采用同一回退值并在简报中显式标注。

## 四、第二阶段设计：协议直送（设计就绪，暂不实施）

简报的交付终点今天是剪贴板。仓库平台源码存在会话协议入口：官方命令
行入口以 stdio 方式提供会话创建、消息发送、流式通知与中断恢复；编程
创建的会话在发出首条消息前不落库，发出后与界面创建的会话完全同权；
侧栏只是会话索引的订阅者，编程创建的会话必然出现在界面；协议层把
子代理会话设为只读，注入只能走顶层对话这条可审计通道。

第二阶段把交付改为协议直送：简报作为新会话首条消息发出，会话即从
草稿提升为正式会话，简文同时成为该会话第一条可查记录，注入动作本身
入会话库留档。未派发的预灌简报会话保持草稿态不落库，与账本认领租约
语义同构。子代理只读闸门为红线体系提供平台层构造级保证，与本仓库
程序性检查互补。

实施前置两项。其一，本机探测结果：官方桌面版安装未在系统命令搜索
路径暴露命令行入口，应用资源目录亦无对应可执行文件，本机暂不可
直送，须在装有命令行入口的环境实施。其二，派发动作保持机主显式
命令，不做自动拉起会话的自动化，派发事件记入 items_registry/events.json
台账。两项满足后，brief.py 增加发送开关即为第二阶段落地。

## 五、判据对照

其一，新会话凭简报零追问开工：简报含路线身份、第一条可领事项及认领
命令、开工卡现行全文、禁区、红线、命令速查，且开工卡本身指示新会话
自跑看板核实现状，简报陈旧风险被双重覆盖。其二，简报内容全部可追溯
账本：第二节逐板块给出来源文件，生成器无内嵌数据。其三，生成器本地
零依赖：仅标准库，见第三节验证记录。销项后首次真实派发若发现缺件，
按开工卡第八条走待审队列登记，不在本判据内预留例外。
