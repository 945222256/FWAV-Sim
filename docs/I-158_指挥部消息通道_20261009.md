# I-158 指挥部消息通道（2026-10-09）

> 事项 I-158：成员间留痕传话与群聊视图。依据机主 2026-10-09 会话
> 提出的群聊与传话需求。施工：L5 队。判据三条冻结于事项登记。

## 一、实现

云端新表 console_messages（时刻、发送方、接收方、关联事项号、正文
五要素），两个接口：POST /api/console/message 发送（消息表写入并
同步写一条 console_events 台账，动作 note）、GET /api/console/messages
拉取（近二百条消息正序加事件台账尾百条，台账可查的读取口）。前端
控制台第四页签"消息"：群聊流（发送方、路线章、事项号、时刻、正文）
五秒轮询加底部发送栏（接收方路线下拉十线加指挥部、关联事项号可填、
正文必填），身份取登录会话经 whoami。样式继承全站令牌。

## 二、判据核验（云端实测 logs/i130_check/i158_check.js）

判据一（指挥部成员可按路线互发留痕消息并在控制台查看消息流）：接口
面发两条不同路线不同事项号消息成功，界面面以真实键盘输入在消息
页签经选择器选 L5、正文键入、点发送，行数六变七，提示"已发送
（消息 #7，台账已记）"。

判据二（每条消息含发送方、接收方、时刻与关联事项号）：流内消息
逐条五字段核验 PASS（实例：sender=anni、recipient=L1/L3、
item_id=I-125/I-148、ts 与正文在案）。

判据三（全部消息入事件台账可查）：console_events 台账尾含全部
六条消息的 note 记录（实例 seq 10：消息#6 发送方 anni → 接收方
L3），台账随消息接口下发可查。截图 logs/i158_page.png。

## 三、边界

其一，接收方粒度为路线（十线加指挥部），对人名粒度的私聊待机主
提出后另立；其二，消息不推送（轮询五秒），服务器推送通道接入归
I-148 追溯抽屉同期的通道优化；其三，测试消息七条留存云端可查，
为验收证据一部分。
